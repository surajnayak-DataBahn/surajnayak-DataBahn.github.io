How I work

The principles I bring to every platform, and the designs that put them into practice.

  • One paved path beats ten exceptions

    I make the standard way the easiest way. Teams adopt a path that saves them time, so I invest in templates, shared pipelines and one release flow instead of reviewing every bespoke setup.

    Seen in: the DataBahn release path, the LaunchPad portal, the Roku mesh onboarding pipeline

  • Every incident ends in a platform fix

    A runbook only helps the next on-call engineer. I close the loop with a change to the platform, so the same class of failure cannot recur.

    Seen in: DataBahn incident command, the Cargill DR and chaos programme

  • Identity, not secrets

    Long-lived keys are an incident waiting to happen. I replace them with workload identity and single sign-on, and keep the access model in code where it can be reviewed.

    Seen in: workload identity at Roku, Entra ID single sign-on at DataBahn

  • Measure delivery before changing it

    I start with DORA metrics and real bottleneck data, then change the process. This keeps platform work tied to outcomes that teams and leadership can both see.

    Seen in: DORA tracking at DataBahn, delivery metrics in LaunchPad

  • Cost is a reliability signal

    I show each team what it spends, set guardrails, and size capacity from real usage. Waste and fragility often have the same root cause.

    Seen in: the DataBahn cost audit, the AiDash FinOps engine

Designs I made the standard

Three reference designs I set as the default way of working for the teams I supported.

One release path

Every service ships one way, to every deployment.

  1. Release or hotfix branch is merged
  2. Merge mints a versioned tag
  3. Argo CD syncs the tag to each deployment
  4. SaaS, customer cloud and on-prem run the same release

Keyless workload access

Pods reach cloud APIs with no stored credentials.

  1. Pod runs as a Kubernetes service account
  2. Cluster issues a short-lived OIDC token
  3. AWS or GCP exchanges it for a scoped cloud identity
  4. No long-lived keys to leak or rotate

Progressive delivery

A bad release reaches a few users, not all of them.

  1. Admission policy rejects non-compliant manifests
  2. Argo Rollouts starts a small canary
  3. Traffic shifts to the new version step by step
  4. One step reverts to the last good revision
